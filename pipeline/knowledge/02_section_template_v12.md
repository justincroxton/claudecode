**1.2 Agency Voice ****&**** AI Elimination Rules**

Every proposal must sound like Propellant Media wrote it — not a language model. The Parkland College proposal is the gold standard for voice. Re-read it before drafting any new proposal.

**Voice Principles**

- **Direct and specific:**** **’We geofence every high school in your service area’ — not ‘Propellant Media implements advanced geofencing technology across educational institutions.’

- **Confident without boasting:**** **State what we do and what happened. Let the numbers speak. If it reads like a press release, rewrite it.

- **Institution is the hero:**** **The college succeeds. We are the partner that makes it happen. Frame every section around their goals, not our credentials.

- **Short paragraphs:**** **3-5 sentences maximum. If a paragraph runs longer, break it up. Evaluation committees are reading 10+ proposals. Make ours scannable.

- **Clean bullets:**** **Bold label + dash + one sentence of substance. No nested sub-bullets unless absolutely necessary. Every bullet earns its spot.

| **BANNED WORDS** | **Leverages, leverage, utilizes, utilize, comprehensive suite, robust, cutting-edge, state-of-the-art, holistic approach, synergies, synergize, spearhead, end-to-end, best-in-class, empower, seamlessly, seamless. If any of these appear in a draft, rewrite the sentence. Full substitution table in Part 5.** |

**1.2a Section Depth & Intro Paragraph Rule (NEW v12.0)**

Two non-negotiables for every section, learned from the NECC review:

| **RULE** | **Every section opens with a real intro paragraph — never a single orphan sentence.** Open with at least one substantive paragraph (3-6 sentences) that frames the institution's situation and what this section delivers, BEFORE any bullets, tables, or sub-headers. A lone one-line lead-in reads thin and unfinished. (Media Plan's mandatory 3-paragraph opener in §14 is the strongest example of this discipline — apply the spirit of it everywhere.) |
| --- | --- |
| **RULE** | **No section may be a half-page. Minimum one full page per section.** If a drafted section lands at half a page, it lacks breadth and context — expand it with institution-specific framing, a "what this means for [institution]" angle, and where it helps, one customized graphic that tells a bigger story tied to the specific college or university. A graphic is not filler; a well-built visual (process loop, funnel, calendar, decision cycle) earns its place and lifts a thin section into a substantive one. Thin sections are a documented loss signal — a committee reads half a page as "they phoned this one in." |

**1.3 TOC Mode Classification Protocol**

Every TOC recommendation must open with an explicit Mode classification. Do not draft any proposal content until Justin or Erin confirms the TOC mode.

| **Mode** | **When to Use** | **What to Do** |
| --- | --- | --- |
| Mode A | RFP prescribes exact section order | Follow their format verbatim. Map our standard sections into their structure as subsections. Non-compliance = disqualification risk. (Wor-Wic, Atlantic Cape, Empire State were Mode A.) |
| Mode B | RFP is silent on structure | Use our standard 19-section Parkland model with exact titles from Part 3. This is our default and our strongest format. (Parkland, Montana State Billings were Mode B.) |
| Mode C | RFP names required sections without mandating full structure | Use our standard TOC as the backbone. Insert RFP-required sections at logical positions using the RFP’s exact titles. (CU Boulder, Collin College were Mode C.) |

| **DECISION PROTOCOL** | **State which mode and cite the specific RFP section that determines it (e.g.,**** ****‘****Mode A — Section 4D states proposals must be organized in the following format****’****). Wait for Justin or Erin confirmation before drafting. If Mode A, list the RFP’s required sections and show where PM’s standard sections map into each one.** |

**1.6a Divider ****&**** Front-Matter Rendering Spec (LOCKED v9 — read before every build)**

These rules exist because divider and front-matter rendering has been the single most repeated source of rework. Follow them exactly. Build the document as MULTIPLE docx sections, not one — each divider/overlay page is its own section.

**A. Static section dividers (Cover Letter, Executive Summary, and all divider_01–20 PNGs)**

- Each static divider is its OWN docx section with margins set to ZERO on all four sides (top/right/bottom/left = 0).

- The divider image MUST be placed as a FLOATING image, anchored to the PAGE (relativeFrom = page on BOTH axes), at horizontal offset 0 and vertical offset 0 (true 0,0 page corner), with behindDocument = true and allowOverlap = true.

- Do NOT place the divider as a plain inline image in a centered paragraph. Inline placement inherits paragraph line-height and leaves a white sliver at the top and clips the bottom — this is the recurring “divider not fixed to the page” bug.

- Image size = full page: 8.5 in x 11 in (816 x 1056 px at 96 dpi). The image is full-bleed, edge-to-edge, with NO white margin anywhere.

- Each divider section MUST set an explicit EMPTY header and EMPTY footer. If you omit them, the section inherits the running header/footer from the previous content section, which pushes the image down and breaks the full bleed (this was the “AI/emerging divider not fixed” bug).

**B. Text-overlay front-matter pages (AA Cover, AC Growing Enrollment, Page 3 Creative Samples, AD Table of Contents)**

- Background image = full-bleed, pinned to the page at 0,0 exactly like a static divider (floating, relativeFrom page, behindDocument true, 816x1056 px). The IMAGE bleeds to the edges.

- The TEXT on top is INSET, not bled. Set the section margins to NORMAL (1 inch / 1440 twips) so the overlay text aligns with the white content pages. Add a small extra left indent (~360 twips / 0.25 in) so text sits slightly right of the left edge.

- Overlay text is LEFT-ALIGNED, never centered. (Cover title, RFP line, submission lines; Growing Enrollment headline + 2 paragraphs; TOC title + entries — all left-aligned and inset.)

- Each overlay section also gets an explicit EMPTY header and EMPTY footer.

- If a background asset is busy/light in the text zone and legibility suffers, the correct fix is to swap to a darker background asset — do NOT drop a hard-edged opaque rectangle behind the text (it looks worse than clean text).

**C. TOC entry paragraphs**

- Right tab stop with dot leader at ~8900 twips (fits inside the 1 in margins). Top-level entries: bold, white. Sub-entries (appendix): regular, light grey (#DCDCDC). Top-level left indent ~360 twips; sub-entry left indent ~1080 twips.

- Verify every entry shows its page number AND a dot leader after rendering — if the tab stop is past the right margin the page numbers disappear.

**D. Mandatory visual QC after every build**

- Render to PDF and visually inspect: page 1 cover (text left-inset, image full-bleed), the Growing Enrollment and TOC overlays (text inset, image full-bleed), the Cover Letter divider and at least two mid-document dividers (full-bleed 0,0, NO header/footer, no white sliver), and at least one bullet page (marker ~0.4 in right of paragraph start, black marker) and one table that spans a page break.

**1.7 Bullet Point Standards**

| **INDENT VALUES (LOCKED v9)** | **LOCKED METHOD: Do NOT rely on Word auto-numbering (docx-js numbering config) for bullets — docx-js can silently drop the level's paragraph indent/tab, so the doc falls back to a default bullet with a wide marker-to-text gap and a non-indented dot. Instead, render each bullet as a LITERAL glyph: start the paragraph with a run of '•' + a tab character, then the text runs. Set the PARAGRAPH directly to indent { left: 864, hanging: 288 } with a LEFT tab stop at position 864. Result: the marker (dot) sits at left minus hanging = 576 twips = 0.4 inch (indented right of where body paragraphs start), the tab pulls the text to 864 right after the dot (tight gap), and wrapped lines align under the text at 864. Marker color MUST be BLACK (000000), never brand red. This literal-glyph method renders identically in Word AND Google Docs. VERIFY visually every time: confirm the DOT itself (not just the text) is indented ~0.4 inch and the gap between dot and text is tight.** |

**1.8 Required ****&**** Mandatory Extraction Protocol (NEW v8)**

Step 1 of every RFP read — before drafting any structure or TOC — is a grep-and-extract pass for required language. This was the single biggest source of mid-draft rework in 2025.

**Trigger Words to Extract**

- MUST, REQUIRED, MANDATORY (in any case)

- shall, will be required to, is required to

- must include, must address, must be submitted

- non-responsive, will be deemed non-responsive, disqualified

- minimum qualification, minimum requirement

- at a minimum, no later than, by [date]

**What the Extraction Produces**

A Required Items table at the top of the Questions Answered Document. This table is locked before any TOC structure is recommended. Format:

| **#** | **RFP Section** | **Required Item (Verbatim)** | **Where in Our Response** |
| --- | --- | --- | --- |

| 2 | … | … | … |

| **RULE** | **The TOC and section structure are built AFTER the Required Items table is locked, not before. If a required item has no logical home in our standard sections, add a new section using the RFP’s exact title. Never bury a REQUIRED item in a paragraph — it gets its own subsection at minimum.** |

**1.14 Mandatory / Required Sections Protocol**

If the RFP explicitly states a section is mandatory or required — and it is NOT already covered by our standard sections — add it as an ADDITIONAL section. Write a 2-3 page response using the RFP’s own section title verbatim. Do NOT duplicate an existing section. Flag every mandatory section with a [REQUIRED BY RFP] callout.

**Non-Core Services Rule**

When the RFP requires responses to services outside our core (helpdesk, student support, faculty support, market research), never skip them — even if we don’t provide that service in-house. Frame non-core services as fee-for-service add-ons. Lead with what we actually deliver (24-hour response, weekly calls, dashboards, melt-prevention campaigns). Position optional modules at the bottom.

Always check Q&A addendums for signals about what the institution actually wants vs. what the RFP template asks for. UNCP said ‘enrollment marketing specialist, not OPM’ in Q&A #5 — that changed the entire positioning. The Q&A often reveals the real evaluation criteria.

**2.1 Global Divider Formatting Rules**

- **Page size:**** **8.5 x 11 inches (US Letter). Never A4.

- **Position:**** **x-axis 0, y-axis 0 (top-left corner of page).

- **Sizing:**** **Fit to page (full bleed). Render at **816 x 1056 px (8.5" x 11" at 96 DPI)**. CRITICAL: docx-js ImageRun transformation dimensions are interpreted as PIXELS at 96 DPI, NOT points at 72 DPI. The old 612 x 792 value rendered every divider at ~75% of the page with a white margin border — the recurring "divider not fit to page" bug. Use 816 x 1056. This matches the spec in 1.6a. Source art in /mnt/project/ is 952 x 1232 px at an exact 8.5:11 ratio — render at 816 x 1056, never re-compress.

- **DPI preservation:**** **Insert dividers at their source resolution. Do NOT re-compress or resize down. Pixelated dividers are immediate rework. Source files in /mnt/project/ are already at production DPI — use as-is.

- **Image wrapping:**** **Behind text (BEHIND_DOCUMENT) for text-overlay dividers. In line with text (full page, no wrap) for static dividers.

- **Page break:**** **Both before AND after every divider so it occupies its own page.

**1.6b   Callout ****&**** KEY TAKEAWAY Box Separation (LOCKED v10)**

Callout boxes (DATA-DRIVEN, GOVERNANCE, AUTOMATION, OPTIMIZATION IN ACTION) and KEY TAKEAWAY boxes are two-column shaded tables. When one is placed immediately after another table (e.g. a Full-Funnel or channel table, or back-to-back case-study boxes), it visually fuses with the table above and reads as a stray final two-column row. RULE: every callout/KEY TAKEAWAY box MUST be preceded by a spacer paragraph (empty paragraph, spacing before ~160 / after ~80) so it is clearly its own free-standing element with visible separation from whatever precedes it. Implementation: the callout() and keyTakeaway() helpers each RETURN an array [spacerParagraph, table]; the add() helper flattens arrays so both elements are inserted. Never emit a callout/KEY TAKEAWAY box flush against the table above it. VERIFY visually: there must be a clear gap between the last real table row and any callout/takeaway box, and between two stacked boxes.
